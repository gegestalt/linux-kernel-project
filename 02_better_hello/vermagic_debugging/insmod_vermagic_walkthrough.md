# insmod vermagic walkthrough (module 02) — hands-on, start to finish

Every command below says exactly which pane to type it in. Follow it top
to bottom, one command per step — nothing here is hypothetical, every
command, every printed value, was actually run. Two scenarios: **Part
A**, a module that loads cleanly (and you watch every check pass, one at
a time, with the actual parameters involved); **Part B**, the same
module built against the wrong kernel, rejected live.

**Rules, once, before you start:**
- **One command per step.** Paste it, Enter, wait for the prompt (`(gdb)`
  or `~ #`) to come back, *then* the next one. Pasting two at once
  reliably breaks — either program will concatenate them into one bogus
  command.
- `continue` in gdb means "go do the next thing in the *other* pane."
  After typing it, switch panes — don't type anything else into gdb
  until told to.
- Your addresses (`0xffff8000...`) won't match the examples below —
  that's normal, module memory is placed fresh every boot. Match the
  *shape* of the output, not the digits.

## Part A — a module that loads cleanly

### Step 1 — build it

*Regular terminal (a third window, or exit tmux attach with `Ctrl-b d`
and come back with `tmux attach -t kgdb` after).*

```bash
cd 02_better_hello
make -C /home/adiopocere/Desktop/codes/linux_mainline M=$(pwd) modules
```

**What just happened:** three separate object files got linked into
`better_hello.ko` with one `ld -r` — `better_hello.o` (your compiled
source — contributes `license=`/`author=`/`description=` to `.modinfo`),
`better_hello.mod.o` (generated by modpost — contributes `name=`/
`depends=`/`srcversion=`, plus a CRC table for every symbol you import),
and `.module-common.o` — a file that isn't "yours" at all, shared across
*every* module built in this run, and the **only** place
`MODULE_INFO(vermagic, VERMAGIC_STRING)` gets emitted. Confirm that
split for yourself:

```bash
readelf -p .modinfo .module-common.o
```

```
String dump of section '.modinfo':
  [     0]  vermagic=7.2.0-kgdb-debug+ SMP preempt mod_unload modversions aarch64
```

That's this object's entire `.modinfo` contribution — `vermagic` never
touches your source file or modpost's generated one.

### Step 2 — read the vermagic string

```bash
modinfo better_hello.ko | grep vermagic
```

```
vermagic: 7.2.0-kgdb-debug+ SMP preempt mod_unload modversions aarch64
```

Every token is a direct readout of *this build's* Kconfig: `SMP` =
`CONFIG_SMP`, `preempt` = `CONFIG_PREEMPT_BUILD`, `mod_unload` =
`CONFIG_MODULE_UNLOAD`, `modversions` = `CONFIG_MODVERSIONS`, `aarch64` =
the arch, `7.2.0-kgdb-debug+` = `UTS_RELEASE`. Flip any one of those
Kconfig options and this string changes — even against the exact same
kernel commit.

### Step 10 — stop 1: `check_modstruct_version` — the check that actually decides pass/fail

**Pane: gdb** — already sitting here:

```
Thread 2 hit Breakpoint 2, check_modstruct_version (info=..., mod=0x...)
    at kernel/module/version.c:77

```
print mod->name
```

```

**What this checks:** not the vermagic string — one hardcoded symbol
name, `"module_layout"`. It's a deliberately empty function, exported by
the kernel itself, whose only job is to have its *parameter types*
(`struct module`, `struct modversion_info`, `struct kernel_param`,
`struct kernel_symbol`, `struct tracepoint`) fingerprinted into one CRC.
`continue` into the lookup that resolves it:

```
continue
```

```
Thread 2 hit Breakpoint 3, find_symbol (fsa=fsa@entry=0x...)
    at kernel/module/main.c:392
```

```
print *fsa
```
```
$2 = {name = 0x... "module_layout", gplok = true, warn = false,
      owner = 0x0, crc = 0x0, sym = 0x0, license = NOT_GPL_ONLY}
```

Input fields set (`name`, `gplok`), output fields still zero. `finish`
this call and look at the same struct again from the caller's frame:

```
finish
```
```
print fsa
```
```
$3 = {name = 0x... "module_layout", gplok = true, warn = false,
      owner = 0x0, crc = 0x..., sym = 0x..., license = NOT_GPL_ONLY}
```
```
print/x *fsa.crc
```
```
$4 = 0x83caa58a
```

**That number is the currently running kernel's own, live-computed CRC**
for `module_layout` — read straight out of `vmlinux`'s own export table
(`owner = 0x0` because the kernel image owns it, not any loaded module).
It gets compared, next, against the CRC *this module* recorded for that
same name when it was built:

```
finish
```
```
Value returned is $5 = 1
```

**`1` = pass.** The module's own recorded CRC and the kernel's live one
matched. This — not the vermagic string — is what actually rejects a
module built for the wrong kernel (Part B proves it).

Same string, two different sources: `modmagic` was just read, live, out
of *this loading module's own* `.modinfo` bytes; `vermagic` is the
kernel's own static compiled-in copy. See the raw bytes `modmagic` was
pulled from directly — this is a plain linear scan over `tag=value\0`
pairs, no lookup table involved:

```
x/8s (char*)info->hdr + info->sechdrs[info->index.info].sh_offset
```
```
0x...:	"description=A simple hello World Linux Kernel Module"
0x...:	"author=guguali"
0x...:	"license=GPL"
0x...:	"srcversion=B4F7C2CAFBE545E9ADB188E"
0x...:	"depends="
0x...:	"name=better_hello"
0x...:	"vermagic=7.2.0-kgdb-debug+ SMP preempt mod_unload modversions aarch64"
0x...:	"\"\006"
```

(Last line is scan overrun past the section's real end — harmless, `x/8s`
doesn't know where `.modinfo` stops.) `info->index.info` is the real ELF
section-header index of `.modinfo` in *this* `.ko` — check it against
`readelf -S better_hello.ko`, it'll be the same number:

```

```
```
$8 = 20
```

### Step 12 — stop 3: `same_magic` — the actual comparison

```

```
```
Thread 2 hit Breakpoint 5, same_magic (
    amagic=... "7.2.0-kgdb-debug+ ...", bmagic=... <vermagic> "7.2.0-kgdb-debug+ ...",
    has_crcs=true) at kernel/module/version.c:99
```

```

```
```
Value returned is $9 = 1
```

**The part that actually surprised me writing this:** `same_magic()`'s
real body —

```c
int same_magic(const char *amagic, const char *bmagic, bool has_crcs)
{
	if (has_crcs) {
		amagic += strcspn(amagic, " ");   // skip past the FIRST WORD of each
		bmagic += strcspn(bmagic, " ");
	}
	return strcmp(amagic, bmagic) == 0;
}
```

`has_crcs=true` here (it's literally `info->index.vers` — non-zero
because this module has a `CONFIG_MODVERSIONS` `__versions` section) — so
both strings get their **kernel-release word skipped entirely** before
comparing. Only the flag words after it (`SMP preempt mod_unload
modversions aarch64`) actually matter. Proven outside the kernel, no
ambiguity:

```bash
# not tmux — regular terminal, run this any time
cat <<'EOF' > /tmp/same_magic_test.c
#include <stdio.h>
#include <string.h>
static int same_magic(const char *a, const char *b, int has_crcs) {
    if (has_crcs) { a += strcspn(a, " "); b += strcspn(b, " "); }
    return strcmp(a, b) == 0;
}
int main(void) {
    printf("%d\n", same_magic("7.2.0-kgdb-debug+ SMP preempt mod_unload modversions aarch64",
                               "7.0.0-30-generic SMP preempt mod_unload modversions aarch64", 1));
}
EOF
gcc -o /tmp/same_magic_test /tmp/same_magic_test.c && /tmp/same_magic_test
```
```
1
```

Two completely different kernel releases read as a vermagic *match* once
CRCs are in play. Not a bug — `check_modstruct_version` (step 10) already
does a strictly more precise ABI check, so the release word is redundant
here; `same_magic()` only still enforces the qualitative flags the CRC
machinery can't express.

## What this proves

- `vermagic` comes from exactly one place — `scripts/module-common.c`,
  compiled once per build, linked into every `.ko` from that run — never
  from modpost's per-module `.mod.c` (step 1).
- `check_modstruct_version()` — a live CRC compare on one symbol,
  `module_layout` — runs *before* the vermagic check and is what actually
  decides whether a module built for a different kernel gets rejected
  (Part A step 10, Part B steps 7–8). It's not special-cased: it's the
  exact same `find_symbol()` + `check_version()` machinery every real
  imported symbol goes through too (Part A step 13, `_printk`).
- `get_modinfo()` fetches the vermagic string with a plain linear byte
  scan over the module's own raw `.modinfo` section — no lookup table,
  no relocation (Part A step 11, live-dumped with `x/8s`).
- `same_magic()` deliberately skips the kernel-release word once
  `CONFIG_MODVERSIONS` CRCs are present — proven live and reproduced
  standalone outside the kernel (Part A step 12). The string everyone
  actually stares at in `modinfo | grep vermagic` output isn't the part
  doing the real work.
- Verified twice, live, on the real debug kernel: once where every check
  passes end to end (Part A), once where the very first kernel-ABI check
  catches a genuinely-wrong-kernel build before the vermagic string
  comparison this whole exercise is nominally about ever runs (Part B).
